# 错误模型（结果形状契约）

> 状态：**生效中**（P0-2 第一步，2026-10-25）
> 适用范围：`lib/` 下所有对外返回结果的函数（路由 handler、领域函数、CLI 子命令）
> 机械保障：`scripts/lint.mjs` 的 R5 规则（`{ ok: false }` 必须说明原因）+ `lib/result.js`

---

## 1. 三种值，不要混

| 种类 | 用途 | 形状 | 例子 |
|---|---|---|---|
| **成功结果** | 一次操作的返回值 | `{ ok: true, ...payload }` | `{ ok: true, applied: 5 }` |
| **失败结果** | 一次操作的返回值 | `{ ok: false, error, detail? }` | `{ ok: false, error: "no-persona" }` |
| **诊断记录** | 描述「某个东西现在是什么状态」 | `{ status, reason }` | `{ status: "na", reason: "opt-out" }` |

**诊断记录不是失败结果**。`reason` 属于诊断（解释为什么是这个状态），`error` 属于失败（这次调用没做成）。
把诊断记录改成 `{ok:false, error}` 是错的，把失败结果写成 `{ok:false, reason}` 也是错的。

---

## 2. 成功结果

```js
{ ok: true, ...payload }
```

- `ok: true` 的含义是：**这次调用的主要目标达成了**。
- 如果有「不影响主要目标、但用户应该知道」的问题，**必须**放进 `warnings: string[]`，
  不允许只写进日志或直接吞掉。
- 反例（4.5.34 的真实缺陷）：插件树删掉了，但 profile 登记没撤干净，函数返回 `ok: true`
  且没有 warnings —— 界面报「已卸载」，用户以为干净了。

---

## 3. 失败结果

```js
{ ok: false, error: "<机器码>", detail?: "<人话>", ...上下文 }
```

| 字段 | 要求 |
|---|---|
| `error` | **必填**。稳定的机器码，kebab-case，**不要放句子**。调用方靠它分支，用户看不到它 |
| `detail` | 选填。给人看的一句话（可含原始异常信息）。UI 展示用 |
| 其余键 | 允许。但**不得**再用 `reason` / `err` / `message` / `success` 表达失败原因 |

机器码举例：`no-persona` / `no-prefix` / `read-failed` / `busy` / `not-plugin` / `unsafe-path`。

---

## 4. 禁止清单

| 禁止 | 为什么 | 怎么改 |
|---|---|---|
| `{ ok: false }`（没有 `error`） | 调用方无从判断原因，日志里也查不到 | 补 `error`；确实无原因说明就是设计错误 |
| `{ ok: false, reason }` | 与诊断记录混淆，两套名字做同一件事 | `reason` → `error` |
| `{ ok: false, error: "中文长句" }` | 机器码和展示文案混在一起，调用方只能做字符串匹配 | 码放 `error`，句子放 `detail` |
| `{ ok: true, error: "..." }` | 自相矛盾；调用方会按 `ok` 走成功分支，错误被丢掉 | 要么 `ok:false`，要么把非致命信息放 `warnings` |
| 跨 HTTP 路由边界 `throw` | 宿主会把未捕获异常变成一个 500 空响应，前端拿不到原因 | handler 内 catch 并返回失败结果 |
| `return null` / `return undefined` 表示失败 | 与「没有值」无法区分 | 返回失败结果 |

---

## 5. 迁移约定

1. **新代码**：直接用 `lib/result.js` 的 `okResult()` / `failResult()`，不要手写字面量。
2. **存量代码**：按文件分批改，每批一次全量测试。判据**不是**「`reason` 计数下降」——
   `reason` 在诊断记录里是正确用法（见 §1、§8），要迁的只有**失败结果里的 `reason`**。
   真正被机械保证的是「不得新增 `{ok:false}` 缺 `error`」（R5）。
3. **兼容**：跨模块边界暂时无法一次改完时，消费方用 `normalizeResult()` 兜底，
   生产方按批次迁移。`normalizeResult()` 只做**兼容**，新代码不得依赖它产生 legacy 形状。
4. **诊断记录**：`patchStatus` 等状态结构保持 `{ status, reason }`，**不要**迁到 `error`。

---

## 6. 机械保障

| 规则 | 位置 | 拦什么 |
|---|---|---|
| R5 `bareFailure` | `scripts/lint.mjs` | 对象字面量里出现 `ok: false` 但整个字面量没有 `error` / 展开（`...`） |
| `test/result.test.mjs` | 单测 | `result.js` 的构造与归一化行为 |
| 基线棘轮 | `.lint-baseline.json` | 存量违规不清零也能过，但新写的不能欠 |

R5 用「找到 `ok: false` 所在的最近一层 `{...}`，检查其中是否有 `error` 或 `...`」判定；
字符串/模板里的花括号可能造成误判，遇到时改写成 `failResult()` 即可，不要放宽规则。

## 8. `reason` 存量分类（2026-10-26 实测，38 处）

统计口径：`lib/` 下除 `core.js`（47 处，全部诊断记录）与 `lib/patches/`（9 处，宿主源码字符串）之外的 `reason:` 出现点。

| 类别 | 处数 | 文件 | 判定依据 |
|---|---|---|---|
| **诊断记录** | **24** | `extract-asar` 7、`refusal-retry` 7、`host-clean` 6、`redteam/index` 2、`uninstall` 2 | 判定键是 `dropped` / `retry` / `installed` / `clean` / `changed`，`reason` 解释「为什么是这个结果」。**成功路径也带 reason**（`{clean:true, reason:"marker"}`、`{retry:false, reason:"ok"}`）——改成 `error` 会把成功写成失败 |
| **纯数据 / 字段名 / 补丁字符串** | **13** | `index` 6（`fastpath_will_use_reason` / `fastpath_active_reason` 是 `/status` 字段名）、`redteam/tools` 2（工具入参 schema + `capped_reason`）、`hooks-deny` 1（注入给宿主的补丁字符串）、`store-core` 4（资产/计分数据字段 + 归档注记） | 不是返回值里的错误键 |
| **外部契约** | **1** | `redteam/ui.js`（宿主 pre-step hook 的 `{kind:'reject', reason}`） | 字段名由宿主定义，改了就破坏 hook 协议 |
| **应迁移为失败结果** | **0** | — | — |

**结论：P0-2 第二批不需要改代码。** 原计划的「38 处待迁移」把「所有 `reason:`」当成了「失败结果里的 `reason`」；
按契约分类后，真正属于失败结果的是 0 处。

复核命令（逐文件计数，减去 `core.js` 47 与 `patches/` 9 即得 38）：

```bash
grep -rc "reason:" lib/ --include=*.js | grep -v ":0$"
```
