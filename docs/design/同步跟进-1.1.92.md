# 同步跟进 dsh-purge 1.1.92：取精华 / 去糟粕方案

> 对象：`G:\AI PGRM\DSH\plugins\Xsdsh-purge-next`（Xsdsh-purge-next 4.6.11-next.2）
> 参照：`~/.dsh/profiles/next/node_modules.bak-rebuild-2026-11-07T15-30-10-479Z/dsh-purge`（dsh-purge 1.1.92）
> 实测宿主：0.2.2-rc.1（app.asar 内 340 个 `@deepseek-ai/*` 子包全部 0.2.2-rc.1）

## 0. 结论

不整体 rebase，不 cherry-pick 上游提交。两棵树已结构性分叉（上游独有 9 个模块、fork 独有 15 个模块 + 4 个子目录、core.js 差 80 KB），合并等于重写。做法是**按能力点定向移植**：

- **取 6 项**，其中 2 项 P0 属于「装了就起不来」级别（预设指针残留、web 残留进程）。
- **舍 5 项**，头号是上游 40 KB 自更新——跑一次就把 fork 覆盖成上游，fork 独有模块全灭。
- **锁 6 项 fork 优势**，同步时只允许「新增文件 + 定点接线」，不许整文件覆盖同名文件。

## 0.1 主体判定：以 next 为主体

**主体 = `Xsdsh-purge-next` 4.6.11-next.2**（profile `next` 里实装的那个），上游 1.1.92 只是**料源**，不是基线、不是主干、不是回推目标。

| | 主体 next | 料源上游 1.1.92 |
|---|---|---|
| 装在哪 | `~/.dsh/profiles/next/node_modules/Xsdsh-purge-next` 4.6.11-next.2 | 备份目录 `…/profiles/next/node_modules.bak-rebuild-…/dsh-purge` 1.1.92 |

| 与谁并存 | 原版 `Xsdsh-purge` 4.6.11-alpha 跑 profile `desktop`（rc.5） | 就是那一条线 |
| 数据目录 | `$DSH_HOME/Xsdsh-purge-core` | `$DSH_HOME/dsh-purge` |
| 自有域 | patches 分表 / redteam / reverse / routes / ui / 三套预设 | 无 |

由此得出三条硬推论，后面每一项吸收都必须遵守：

**推论一：只吸能力，不吸架构。**
上游的目录结构、`core.js` 内联表、`index.js` 的 `registerRoute` / `sendJson` 那一套 HTTP 写法，一律不跟。吸进来的东西要长成 next 的形状。

**推论二：上游对 rc.5 的结论，搬到主体上必须重验。**
上游注释里直接写着版本前提，例如 `anchor.js:118`「rc5 的 refreshContext 会把 required 的 context 从 suppress 里捞回来」—— 这句在主体（rc.4 线）上不成立，子锚点会不会被 suppress 掉必须实测，不能照抄。同理 `subagent-control.js:4-7` 对 `decide()` 顺序的描述、`profile-insert.js` 对 pnpm 大版本的判断，都要在主体实测的环境里复核。

**推论三：命名与数据一律走 next 前缀，物理隔离。**
主体与原版 `Xsdsh-purge` 在同一台机器上并存（不同 profile、不同安装根）。任何从上游搬来的常量如果带 `dsh-purge` 字样，必须改成主体的：

| 上游常量 | 位置 | 主体必须改成 |
|---|---|---|
| `RECORD_DIR = "dsh-purge"` | `web-reclaim.js:18` | `"Xsdsh-purge-core"`（主体数据目录，见 `dshNextCompat.dataDir`） |
| `RECORD_PREFIX = "web-server-"` | `web-reclaim.js:19` | 保留，但文件名前缀加 `xsdsh-` 以免与原版同机同端口互删记录 |
| `MARK = "dsh-purge-web-preflight"`、`IMPORT_LINE` | `bin-preflight.js:12-13` | 改成 `Xsdsh-purge-next-web-preflight`，否则两份插件会在同一宿主安装里抢同一个 sidecar 名 |
| `ANCHOR_SECTION = "dsh-purge:anchor"` | `anchor.js:19` | `"Xsdsh-purge-next:anchor"`（主体已有段名 `Xsdsh-purge-next` / `Xsdsh-purge-next:post`，见 `lib/index.js:330/369`） |
| `CHILD_ANCHOR_CONTEXT` | `anchor.js:20` | 同上加 `-next` 前缀 |

**吸收契约（每一条搬进来的代码都要过）**

1. 返回值走 `lib/result.js` 的 `okResult` / `failResult`，机器码 kebab-case；非致命问题放 `warnings: string[]`。判据文档 `docs/design/错误模型.md`，机械检查 `scripts/lint.mjs` 的 **R5**（裸 `{ ok: false }` 必须带 `error`）。
2. 日志走主体的 `purgeLog`（`lib/index.js:265` 一带）而不是 `console.*`（R2 只放行 `bin/` 与 `scripts/`）。
3. 不做 no-op catch（R1）—— 上游为了「两棵树通用」写了大量 `catch { /* … */ }`，搬进主体必须补上可观测分支或明确注释为什么无害。
4. 配置项两处必须一致：`cordis.patch.yml` 的 insert 块 `config:`（当前 62-78 行那一段）与代码里的归一/默认值。新增 `anchorMode`、`subagentControl` 之类开关要同时落这两处。
5. 注释与文案用简体中文；技术标识（`ctx.effect`、`systemPrompt.section`）保留原文。
6. 不新增上游式 `import "@deepseek-ai/*"`；宿主能力只走注入服务。

**主体自身先要对齐的一件事（P0-0）**

`package.json` 的 `dshNextCompat.verifiedRuntime` 记的是 `0.2.1-rc.4`，但当前实跑的 `resources/app.asar` 里 `@deepseek-ai/*` 子包是 `0.2.2-rc.1`（此前实测 340 个全部同版本）。`engines` 写的是 `>=0.2.1-rc.0 <0.3.0`，形式上还满足，但**验证记录已经落后于实际宿主**。
→ 在吸收上游之前，先用一条命令把真实版本核一遍，并更新 `dshNextCompat.verifiedRuntime` / `dshTarget`，否则后面所有「在主体上实测通过」的结论都建在错的宿主基准上。

注入面：`bin-preflight.js` 把 `web-preflight-entry.js` 写成宿主 `lib/dsh-purge-web-preflight.js` sidecar，并在 `bin.js` 顶部插 `import "./dsh-purge-web-preflight.js";`（:13 `IMPORT_LINE`），在 Cordis 激活**之前**执行；`looksLikeSourceCliRoot` 的源码部署只读跳过（:20），asar 密封路径跳过（:23）。回收动作在 `web-preflight-entry.js:87 main()`，`waitGone` 兜底 1500 ms（:154）。

### P2-6 子代理审批事件层兜底 —— `lib/subagent-control.js` 的思路（2886 B）

**上游为什么需要**
宿主给子会话写死 `approvalPolicy: "never"`：`dsh-subagent` 的 `captureDelegatedPolicyOverrides` → `approvalPolicy: "never"`；`dsh-user-approval decide()` 里 `if (effectivePolicy === "never") return "rejected"` —— 这步发生在 `approval/request` waterfall **之前**，任何监听器都救不到（:4-7 注释）。
上游两步：① 监听 `session/event` 的 `approval/policy`，看到子会话的 `never` 就补一条 `ask`（`:42 session.append("approval/policy", { policy: "ask" })`），名额 `MAX_FLIPS = 4`（:17），且 append 失败要退还名额（:44，否则 4 次空转后该会话永远不再补 ask）；② 在 `approval/request` 的 **global** waterfall 里对子会话放行一次（:54 —— 必须 global，因为宿主是 `ctx.waterfall(scopeTarget(req.agent, req.agent), …)` agent 作用域）。

**fork 现状**
fork 走的是**改宿主源码**那条路（`lib/patches/engine.js` 的 approval 替换），覆盖更宽（主会话也管），但依赖字面 pattern —— 宿主 0.2.2-rc.1 上一旦源码变形就整体失配，且失配是静默的。

**定位**
**不替换**现有 patch 表，只作为「patch 失配时的降级通道」：engine 补丁 `patchStatusReady` 为 false 时启用事件层。

**验证**：子代理跑一次需要审批的工具调用；patch 生效走原路；人为破坏 pattern 后应靠事件层放行。
**风险**：中。两条路径同时生效会重复放行一次（无害但日志噪音），需加互斥开关 `subagentControl`，默认跟随 patch 状态。
**next 化改造**：`subagent-control.js:4-7` 对 `decide()` 顺序的描述来自上游那一版宿主；主体在 rc.4 线上，先按 `lib/patches/engine.js` 现有 approval 补丁的实际位置复核「`never` 在 waterfall 之前返回」是否仍成立。成立才保留这个兜底；不成立说明主体现有补丁已覆盖，整项降级为「不加」。互斥开关进 `cordis.patch.yml` insert 块。
